# RHEL 9.7에서 LVM RAID1 기반 OS 구성 - 실무 경험 정리

## 들어가며

고객사 환경에서 서버 HW RAID 컨트롤러 미지원으로 인해 Software RAID(LVM RAID1)를 기반으로 OS를 구성하게 되었습니다. 구성 과정에서 겪은 여러 문제와 해결 방법을 공유합니다.

**시스템 환경**
- OS: RHEL 9.7
- RAID: Software RAID (mdadm/LVM mirror)
- 부팅 환경: Legacy BIOS, UEFI 모두 지원 필요

---

## Part 1: 문제 상황 분석

### 1.1 HW RAID 미지원으로 인한 SW RAID 도입

고객사 환경에서 RAID 컨트롤러 미지원:
- **선택지**: HW RAID 추가 비용 vs SW RAID 구성
- **결정**: Software RAID(LVM/mdadm) 기반 구성

여기까지는 상대적으로 간단했습니다. 문제는 **부팅 영역(OS 영역)에 RAID1을 구성**해야 한다는 점에서 시작되었습니다.

### 1.2 예상 밖의 부팅 모드 불일치

**초기 구성**: Legacy BIOS 기반으로 설계 및 구현  
**고객 환경**: UEFI 부팅 모드 ❌ **심각한 문제 발생**

이 두 부팅 모드의 차이를 이해하지 못하면 부팅 실패로 이어집니다.

---

## Part 2: Legacy BIOS vs UEFI - 핵심 차이점

### 2.1 부팅 메커니즘의 차이

| 항목 | Legacy BIOS | UEFI |
|------|-----------|------|
| 부트로더 위치 | 디스크 MBR(특정 블록) | /boot/efi 파티션 내 .efi 파일 |
| 파티션 요구사항 | MBR, 파티션 스키마 불필요 | GPT, EFI System 파티션 필수 |
| 부팅 파일 | /boot 영역의 grub2 | /boot/efi의 .efi 파일 |
| 마운트 관리 | 자동 처리 | 명시적 마운트 필요 |

### 2.2 grub2-install 명령어의 차이

**Legacy BIOS 설치:**
```bash
# 특정 파티션 지정 불필요, 디스크 자체를 지정
grub2-install /dev/sdb
```

**UEFI 설치:**
```bash
# /boot/efi가 마운트된 파티션까지 명시
grub2-install --efi-directory=/boot/efi /dev/sdb
```

## Part 3: /boot와 /boot/efi 관리 전략 변화

### 3.1 초기 접근: mdadm으로 /boot 구성

**처음 선택한 방식:**
- `mdadm`으로 /boot를 RAID1 구성
- 이유: LVM mirror는 다른 디스크 파티션이므로 /boot와 /boot/efi를 별도로 관리해야 함
- mdadm 사용 시: 자동으로 동기화되어 별도 관리 불필요

**문제 상황**: 고객사에서 mdadm 사용 거부
- 이유: 추가 복잡성, 유지보수 부담
- **결정**: LVM mirror 기반으로 변경하되, 별도 관리 전략 수립 필요

### 3.2 최종 접근: efibootmgr을 이용한 동적 마운트

고객사 요구사항에 따른 최종 해결 방법:

```
/boot, /boot/efi를 각각 다른 디스크에 구성
                    ↓
        부팅 시 현재 부팅된 디스크 확인 (efibootmgr)
                    ↓
        해당 디스크의 /boot, /boot/efi만 마운트
                    ↓
        systemd 서비스로 자동화
```

이 방식의 장점:
- 디스크 fault 시 자동으로 다른 디스크로 부팅 가능
- 부팅 중인 디스크를 명시적으로 파악
- fstab의 고정 UUID 의존성 제거

### 3.3 efibootmgr을 이용한 부팅 디스크 확인

```bash
# 현재 부팅된 디스크/파티션 확인
efibootmgr -v
```

**출력 예시:**
```
BootCurrent: 0000
BootOrder: 0000,0001
Boot0000* UEFI: Samsung 850 EVO 1TB (BCBE)
Boot0001* UEFI: WDC WD10EZEX 1TB
...
```

- `BootCurrent: 0000` → 현재 부팅된 것은 0000번 항목
- 0000번의 디스크 정보를 파싱하여 마운트 대상 결정

## Part 4: 동적 마운트 스크립트 & systemd 서비스

### 4.1 /boot, /boot/efi 동적 마운트 스크립트

**핵심 로직:**

```bash
#!/bin/bash
# 1. 현재 부팅된 EFI 부팅 항목 번호 확인
# 2. 해당 항목의 디스크 정보 파싱
# 3. 예상 파티션 번호로 /boot, /boot/efi 마운트
```

**문제점**: 파티션 번호 매핑이 복잡할 수 있음
- 여러 RAID 구성 시 파티션 순서 불일치 가능
- 디스크별 파티션 번호 일관성 유지 필수

### 4.2 systemd 서비스 등록

**서비스 파일 예시:**

```ini
[Unit]
Description=Mount Boot Partitions based on EFI Boot
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/bin/mount-boot-partitions.sh
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

**등록 및 활성화:**
```bash
systemctl daemon-reload
systemctl enable mount-boot-partitions.service
systemctl start mount-boot-partitions.service
```

## Part 5: RHEL 9.3+ Grubby/BLS 구조 변화

### 5.1 RHEL 9.3 이상의 주요 변화

**이전 방식 (RHEL 9.2 이하):**
```bash
# /etc/default/grub 수정
GRUB_CMDLINE_LINUX="console=ttyS0"

# grub 설정 재생성
grub2-mkconfig -o /boot/grub2/grub.cfg
```

이 방식은 **RHEL 9.3 이상에서 작동하지 않습니다.**

### 5.2 RHEL 9.3+의 BLS(Boot Loader Specification)

**새로운 구조:**

```
/boot/loader/entries/
├── rhel-9.7-x86_64.conf
└── rhel-9.7-x86_64-rescue.conf
```

**원인: GRUB_ENABLE_BLSCFG 설정**

```bash
cat /etc/default/grub | grep GRUB_ENABLE_BLSCFG
# GRUB_ENABLE_BLSCFG=true  ← RHEL 9.3+에서 기본값
```

### 5.3 커널 파라미터 적용 방법

**RHEL 9.3+ 권장 방법 - grubby 명령어 사용:**

```bash
# 커널 파라미터 추가
grubby --update-kernel=ALL --args="console=ttyS0 rd.net.timeout.carrier=5"

# 결과: /boot/loader/entries의 모든 .conf 파일에 자동 반영
```

**동작 원리:**
1. `grubby` 명령어 실행
2. `/boot/loader/entries/` 의 **모든** 커널 .conf 파일 업데이트
3. 다음 부팅 시 자동 적용

**일반적인 실수: /etc/default/grub 직접 수정**
```bash
# ❌ 이 방법은 작동하지 않음 (RHEL 9.3+)
echo 'GRUB_CMDLINE_LINUX="console=ttyS0"' >> /etc/default/grub
grub2-mkconfig -o /boot/grub2/grub.cfg
# 부팅 후 커널에 파라미터 적용 안 됨

# ✅ 올바른 방법
grubby --update-kernel=ALL --args="console=ttyS0"
```

### 5.4 grubby 주요 명령어

```bash
# 현재 설정 확인
grubby --info=ALL

# 특정 커널의 파라미터 확인
grubby --info=/boot/vmlinuz-$(uname -r)

# 기본 커널 확인
grubby --default-kernel

# 커널 파라미터 추가
grubby --update-kernel=ALL --args="console=ttyS0"

# 특정 파라미터 제거
grubby --update-kernel=ALL --remove-args="console=ttyS0"
```

## Part 6: 통합 구성 흐름

### 6.1 전체 구축 절차

```
1. 디스크 파티셔닝 (GPT)
   ├─ /boot/efi: 512MB (EFI System)
   ├─ /boot: 1GB (LVM RAID1 또는 mdadm)
   └─ /: 나머지 (LVM RAID1)

2. RAID 구성 (LVM mirror 기반)
   ├─ /boot, /boot/efi 별도 관리
   └─ LVM RAID1로 root 파티션

3. 부팅 환경 설정
   ├─ grub2-install (각 디스크마다)
   ├─ efibootmgr 확인
   └─ 동적 마운트 스크립트 등록

4. 커널 파라미터 적용
   ├─ grubby로 파라미터 설정
   └─ RHEL 9.3+ BLS 호환성 확보
```

### 6.2 재해복구 시나리오

**디스크 1 장애 발생:**
```
1. 부팅 시 UEFI에서 디스크 2로 자동 부팅
2. efibootmgr 파싱으로 현재 부팅 디스크 식별
3. 마운트 스크립트가 디스크 2의 /boot, /boot/efi 마운트
4. LVM RAID1이 자동으로 재구성 시작
5. 정상 운영 상태 복구
```
